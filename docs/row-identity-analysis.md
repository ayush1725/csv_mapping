# Row Identity and File Shape

Analysis of two questions raised during review:

1. Do all partner files carry a `Member Number` / `Sr No.` row identifier?
2. If not, is the data laid out row-wise or column-wise?

**Method:** header analysis of the 24 partner sample sets in
`data/partner_samples.json`. **Limitation:** headers only — no data rows were
available. Question 2 cannot be fully answered without them; §3 states exactly
what to check.

---

## 1. `Member Number` is required but mostly absent

`Member Number` is one of the 9 required canonical fields. Only **8 of 24**
partners send it.

| | Partners |
|---|---|
| **Present (8)** | MPGB, GGB, Namra, Mathooth, Avanti, Allience, Hello ujjivan feeder, Data loader |
| **Absent (16)** | L&T, Tujbhavani, Sambhavati, Respo, Paisalo, IIFL, Capri g, Uss, Uco, Ubi, Rbl, House loader, Hospital partner, Hello ujjivan standalone, Boi, Agri feeder |

Every partner that sends it belongs to the master-aligned or bare-repeat
family — i.e. those who adopted our template. No partner sending their own core
system export supplies it.

**Two possible explanations, and they lead to different actions:**

| Explanation | Action |
|---|---|
| `Member Number` is generated by us, not supplied by the partner | **Remove it from the partner-supplied required list.** As written, the validation rule would reject 16 of 24 partners. |
| Partners are expected to supply it | 16 partners are being manually completed today — quantify that effort, it may be a large share of the manual work this project targets |

This needs an answer before required-field gating is implemented.

### 1.1 The real universal key is the loan account number

| Candidate | Coverage | Missing from |
|---|---|---|
| **Loan account no** | **23/24** | Sambhavati (metadata block only) |
| Proposal / Application no | 17/24 | Tujbhavani, Respo, Namra, Mathooth, IIFL, Avanti |
| Serial (row counter) | 13/24 | L&T, MPGB, GGB, Respo, Paisalo, IIFL, Avanti, Allience, … |
| Customer ID | 11/24 | L&T, Tujbhavani, Paisalo, Namra, IIFL, Capri g, Uco, Ubi, Rbl, … |
| Member / Policy no | 10/24 | L&T, Tujbhavani, Respo, IIFL, Capri g, Uss, Uco, Rbl, Boi, … |

Recommendation: treat **`Loan A/c No` as the correlation key** for
deduplication, retry and row-grouping.

### 1.2 Serial numbers are not business keys

`Sr. No.`, `Sl.no`, `S No.`, `srNo`, `s_no` appear in 13 partners but identify a
**line in a file**, not a policy. They are not stable across resubmissions and
must not be used for idempotency or deduplication.

## 2. File shape: row-wise confirmed, wide-vs-long open

### 2.1 Column-wise is not a risk

All 24 sample sets are **row-wise** — one entity per row, fields as columns. A
transposed layout would present headers such as `Field | Value1 | Value2`; none
do. No further work is needed on this question.

### 2.2 The open question is wide vs long

**21 of 24 partners send `No. of Lives`. Only 3 have structural room for more
than one insured in a single row.**

| Partner | `No. of Lives` | Insured blocks in the row |
|---|---|---|
| Rbl, House loader | Y | **>1** — `insured_adult2`, `insured_child1`, `insured_child2` |
| Hello ujjivan standalone | Y | **>1** — `Insured 2 First Name/Last Name` |
| MPGB, GGB, Tujbhavani, Respo, Namra, Mathooth, IIFL, Capri g, Avanti, Allience, Uss, Uco, Ubi, Hospital partner, Hello ujjivan feeder, Data loader, Boi, Agri feeder | Y | **1** |

Eighteen partners declare a policy covering N lives while providing exactly one
insured name block. Three explanations are possible:

| # | Explanation | Implication |
|---|---|---|
| **a** | **Long format** — one policy spans multiple rows, correlated by `Loan A/c No` | Each row hitting create-policy produces **N single-life policies instead of 1 policy with N lives** |
| b | Floater — lives are counted, not itemised; Sum Insured is shared | Correct as-is; `Cover Type` (16/24) distinguishes it |
| c | `No. of Lives` is always 1 in practice for these partners | Correct as-is |

**Headers cannot distinguish these.** Data rows are required.

### 2.3 Why (a) would matter beyond header mapping

If a policy spans multiple rows, two existing behaviours break, neither related
to header resolution:

1. **Per-row policy creation** — N rows produce N policies rather than one
   policy with N lives.
2. **The configurable row limit can split a policy across batches.** If a
   3-row policy is chunked between rows 2 and 3, two incomplete policies are
   created. This surfaces only at particular file sizes and batch boundaries,
   making it hard to reproduce.

Point 2 is the more serious: it is size-dependent and non-deterministic from
the operator's point of view.

## 3. The check to run

Against real partner files, using the loan account number as the key:

```sql
-- Does one loan account appear on more than one row?
SELECT loan_account_no, COUNT(*) AS rows
FROM   uploaded_file
GROUP  BY loan_account_no
HAVING COUNT(*) > 1;

-- Does row count per key match the declared No. of Lives?
SELECT loan_account_no,
       MAX(no_of_lives) AS declared_lives,
       COUNT(*)         AS actual_rows
FROM   uploaded_file
GROUP  BY loan_account_no;
```

### Interpreting the result

| Observation | Conclusion | Action |
|---|---|---|
| 1 row per key, lives = 1 | Simple wide format | None — current pipeline correct |
| 1 row per key, lives > 1 | Floater, or itemisation missing | Confirm `Cover Type`; check whether Sum Insured is shared or per-life |
| **N rows per key, lives = N** | **Long format** | Policy assembly must group rows by key **before** enqueue; row limit must chunk on key boundaries, never mid-policy |

### Files to test first

| Partner | Why |
|---|---|
| **Rbl / House loader** | Declares lives *and* has wide multi-life columns — establishes the wide baseline |
| **Ubi / Boi / Uco** | Declare lives with a single insured block — the suspicious pattern |
| **Tujbhavani** | Declares lives with no insured block structure at all |
| **Hello ujjivan standalone** | Has `Insured 2` — partial widening, may indicate a cap of 2 |

---

## 4. Consequences for the plan

| Area | Change |
|---|---|
| Required-field gating | `Member Number` may not be partner-supplied; gate on `Loan A/c No` instead until §1 is answered |
| Correlation key | Use `Loan A/c No` (23/24), not `Member Number` (8/24) or serial numbers |
| Idempotency / retry | Must key on a business identifier; serial numbers are unsuitable |
| Row limit and SQS chunking | If long format is confirmed, chunking must respect policy boundaries |
| Health schema (`health_v1`) | Must decide whether multiple lives are modelled as repeating columns (wide) or repeating rows (long) — this analysis is a prerequisite |

## 5. Status

| Question | Answer |
|---|---|
| Do all files have a row identifier? | **No.** `Member Number` in 8/24; the only near-universal key is `Loan A/c No` at 23/24 |
| Row-wise or column-wise? | **Row-wise, confirmed** — column-wise is not a risk |
| One row per policy, or many? | **Open.** 18 partners show a `No. of Lives` vs insured-block mismatch. Requires data rows to resolve — see §3 |
